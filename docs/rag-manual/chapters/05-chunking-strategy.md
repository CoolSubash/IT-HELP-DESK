# Chunking Strategy

## Why chunk at all

An embedding model compresses a piece of text into one fixed-size vector -- for this project, 1024 numbers, regardless of whether the input text is one sentence or twenty pages. Feed an entire multi-page VPN guide into an embedding model as a single unit, and that single vector has to somehow represent "how to install the client" *and* "how to troubleshoot a connection failure" *and* "what each specific error code means" all at once, averaged together into one point in a 1024-dimensional space. A student's query about one specific error code produces a query vector that's semantically close to only a *fraction* of what that averaged document vector represents -- diluted by everything else the document also talks about. The result is retrieval that's directionally right (a VPN question will still tend to surface VPN documents over WiFi documents) but imprecise in exactly the way that matters most: it can't tell you *which part* of a long document is actually relevant, and a genuinely relevant long document can lose a close race against a shorter, more topically narrow one that happens to average closer to the query.

Splitting a document into smaller chunks before embedding fixes this by giving each embedding a single, coherent idea to represent. A chunk about "VPN-ERR-403: Authentication Failed" produces a vector that's *only* about that -- so a query about an authentication failure scores that chunk highly and correctly leaves the installation-instructions chunk of the same document out of the way, even though both chunks came from the same source file.

## Why not just split every N characters

A naive fixed-character-count split (split every 2000 characters, regardless of what's there) would solve the "one vector, too much content" problem, but introduces a worse one: it has no idea where one idea ends and another begins. It will, with some regularity, cut a numbered instruction list in half -- leaving a chunk that reads "...3. Click OK. 4." with no idea what step 4 actually says, because that text landed in the *next* chunk instead. phase7.md section 5 explicitly asks for boundary-aware splitting, and this is why: a chunk that's syntactically valid text but semantically incoherent is worse than useless for retrieval -- it can score well on a query (it still shares vocabulary with the topic) while handing back content that doesn't actually answer anything.

## The actual algorithm (`backend/app/rag/chunking.py`)

The implementation (`chunk_text()`) works in two passes, deliberately structured so that boundary-awareness comes *first* and size-based packing comes *second*, never the other way around:

**Pass one: split into whole blocks.** The input text is split on blank lines into blocks -- each block being a paragraph, a heading plus the paragraph immediately following it, or a run of bullet-list lines. A heading line by itself is never emitted as its own zero-content block; it's attached to the block that follows it, so `"## VPN Errors\n\nAuth failures happen when..."` stays together as one unit rather than becoming a heading with no content and a content block with no context. This pass never looks at size at all -- it only looks at structure.

**Pass two: pack whole blocks into chunks up to a token budget.** Blocks are then packed greedily: keep adding whole blocks to the current chunk until adding the next one would exceed the configured size limit, then start a new chunk. Critically, a block is *never split* in this pass -- if a block doesn't fit, it starts a new chunk rather than being cut in half. This is what guarantees a chunk boundary never falls in the middle of a bullet list or a short paragraph.

**The one exception: an oversized single block.** If a single block -- one long paragraph with no internal blank lines -- is itself larger than the entire chunk size budget, something still has to give, because that block can't be packed whole and can't be skipped. In that case, and only that case, the block is split at *sentence boundaries* (using a regex that looks for `.`, `!`, or `?` followed by whitespace), packing whole sentences up to the budget. This is a deliberate last resort: it never fires for a normally-structured document (one with reasonable paragraph breaks), and even when it does fire, it still never cuts a sentence in half -- the worst case is a chunk boundary between two related sentences, not inside one.

## Overlap: carrying context across a chunk boundary

Even with boundary-aware splitting, a chunk boundary can still fall between two sentences that depend on each other -- "Restart the VPN client, then try connecting again" split so that "then try connecting again" starts a new chunk with no idea what "then" refers to. To reduce this, each new chunk (after the first) is prefixed with the trailing words of the *previous* chunk's last block, up to a configurable overlap budget. This means the same handful of words appear at the tail of one chunk and the head of the next -- a small amount of deliberate redundancy that keeps each chunk more self-contained when it's later retrieved and shown to a reader (or, eventually, an AI agent) independently of its neighbors, out of original document order.

## Configuration, and why these specific defaults

Chunk size and overlap are both plain function parameters to `chunk_text()`, driven in turn by two settings (`RAG_CHUNK_SIZE_WORDS`, default 600; `RAG_CHUNK_OVERLAP_WORDS`, default 80) rather than hardcoded constants anywhere in the pipeline. phase7.md section 5 is explicit about this: *"Do not blindly assume these values are optimal... Make the values configurable."* These defaults sit inside phase7.md's own suggested starting range (roughly 500-1000 tokens, with 50-150 tokens of overlap) without picking either extreme, but they are not claimed to be the *correct* values for every corpus -- they are a reasonable starting point, and Chapter 15 (Retrieval Evaluation) is explicitly the tool this project provides for actually testing whether a different value helps, rather than guessing: re-run `python -m scripts.evaluate_retrieval` before and after changing either setting and compare the Recall@K/Precision@K numbers.

## Tokens vs. words: an honest approximation

This project has no tokenizer dependency -- no `tiktoken`, no model-specific tokenizer library. Adding one purely to count tokens more precisely than a word count was judged not worth the extra dependency for this phase. Instead, `count_tokens_approx()` estimates token count as `words * 1.3` -- a standard rough conversion factor for English text (roughly 0.75 words per token on average for common tokenizers, i.e. about 1.3 tokens per word), documented explicitly as an approximation rather than presented as exact. Every "tokens" concept referenced anywhere in the chunking module -- chunk size, overlap, the `token_count` column stored per chunk -- is in this approximated unit. If a real tokenizer is added to this project later (for instance, to precisely track cost against a specific LLM's actual token accounting), it's a self-contained change: `count_tokens_approx()` is the one function that would need to change, and `chunk_text()`'s signature and the shape of the `Chunk` objects it returns stay exactly the same.

## The tradeoff, stated plainly

Bigger chunks retain more surrounding context per chunk -- fewer "which specific VPN error is this troubleshooting step even about" ambiguities when a chunk is read in isolation -- but dilute the embedding (more competing sub-topics packed into one vector, worse retrieval precision for a narrow query) and cost more tokens if the chunk is later fed to an LLM. Smaller chunks are the mirror image: sharper, more precise retrieval, but more fragmented context and more total chunks to embed and store per document. More overlap reduces the chance a boundary falls exactly on the information a query needs, at the direct cost of redundant text that gets embedded and stored twice. None of these tradeoffs have a universally correct answer -- they depend on the actual shape of the documents being ingested, which is exactly why the values are configurable and why Chapter 15's evaluation harness exists as the actual mechanism for deciding, empirically, whether a given corpus benefits from different values.

## A worked example, using this project's real seeded content

The `VPN Troubleshooting Guide` (`backend/seed/knowledge_docs/vpn_troubleshooting_guide.md`) is a real, moderately long document with distinct sections: `## Overview`, `## Installing Cisco AnyConnect`, `## Connecting to the VPN`, `## Common VPN Errors` (containing three `###` subsections, including `### VPN-ERR-403: Authentication Failed`), and `## When to Escalate`. At the default 600-word/80-word-overlap settings, this document -- roughly 550-600 words total -- packs into either one or two chunks, depending on exactly how its blocks fall relative to the word budget; when a real ingestion run of this document was inspected via `GET /admin/knowledge/{id}/chunks`, its content stayed grouped along exactly these section boundaries, never splitting a bullet list or a numbered installation step across two chunks. The Worked Example chapter traces this specific document through the complete pipeline, including its actual observed chunk content and a real retrieval query's scored results against it.

## What this module is tested against

`tests/test_rag_chunking.py` (6 tests, pure unit tests requiring no database) verifies every claim made in this chapter directly against the code, not just by inspection: that empty input produces zero chunks; that a short input produces exactly one chunk with correctly computed metadata; that a long, multi-paragraph input actually splits into multiple chunks, each respecting the configured size budget; that overlap is not just configured but demonstrably *applied* (the tail words of one chunk are shown to reappear at the head of the next); that a bullet list short enough to fit isn't needlessly split; and that an artificially oversized single block with no paragraph breaks splits at sentence boundaries, with every resulting chunk verified to end on a sentence boundary (a period), never mid-sentence.
